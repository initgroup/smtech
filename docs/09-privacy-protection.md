# 게시판 개인정보 보호 구현 및 공식 근거

확인일: **2026-10-15 (Asia/Seoul)**. 적용: 시안 1·2·3 공통 Q&A 제목·본문·댓글·답변, SFR-09-05·SFR-09-07. 이 문서는 구현 설명과 운영 이관 지침이며 공공기관 보안 인증서나 법률 적합성 보증서가 아니다.

개인정보 여부는 단순히 번호 형식만으로 결정되지 않는다. 살아 있는 개인을 직접 식별하거나 다른 정보와 쉽게 결합하여 식별하는 정보도 대상이다. 기업 자체의 정보와 기업 담당자의 이름·연락처·주소를 구분해야 한다. 본 게시판은 공개 영역에서 작성자·기업 담당자 필드 자체를 제외하는 보수적 정책을 적용한다. 안내서의 노출 개념에 따라 일반 이용자가 원문을 알아볼 수 있는 상태 자체를 문제로 보며, CSS로 글자를 가리거나 개발자 도구에서 원문이 남는 방식은 보호로 취급하지 않는다.

PDF 3개는 변조하지 않은 공식 파일이다. 출처 URL·검색 확인일·파일 크기·SHA-256은 [provenance.json](../reference/privacy/provenance.json)에 있다. 웹의 SFR-09 우측 “구현된 메뉴 및 적용 기술”에서 실제 파일을 다운로드할 수 있다.

## 3. 검사 및 마스킹 절차

1. HTML은 DOMPurify의 허용 목록으로 정화한다. URL·스타일·data 속성 등에 개인정보를 숨길 수 없도록 속성을 허용하지 않는다.
2. DOM의 텍스트를 추출한다. 태그로 번호를 나누는 우회도 검사하고 개인정보가 발견된 본문은 원래 HTML을 버리고 마스킹 텍스트로 재생성한다.
3. NFKC 정규화, 전각 문자 변환, 보이지 않는 문자·방향 제어 문자 제거, 숫자 HTML 엔티티와 일부 난독화 이메일을 정규화한다.
4. 이메일·휴대/유선전화·주민/외국인등록번호·신용카드·계좌·여권·면허 형식, 긴 개인식별·금융번호 및 `이름:`·`담당자:`·`주소:`와 같은 필드를 검사한다. 안내서 8종 중 건강보험번호도 별도 필드로 분류한다. 생년월일·교육·건강·가족·고용·소득·계정·접속 IP·위치정보는 명시된 필드 값 전체를 숨긴다. 체크섬이 맞지 않는 번호도 의심 정보로 가린다.
5. 이름은 `김○○`, 휴대전화는 `010-****-****`, 이메일은 `***@***.***`로 표시한다. 주민·금융번호와 상세주소는 전체값 숨김 토큰으로 바꾼다. 이름의 성과 전화 식별번호 일부를 남기는 표시용 마스킹이며 익명화나 완전한 재식별 방지로 보지 않는다. 탐지 로그에는 종류·위치만 남기며 원문을 반환하지 않는다.
6. 저장 경로와 공개 출력 경로에서 재검사한다. 메인 노출은 공개 여부·관리자 노출 설정·개인정보 탐지 여부를 별도로 확인한다. 공개 객체는 작성자 식별자·연락처·비회원 비밀번호 등 내부 필드를 복사하지 않는다.

이 규칙은 공식 문서의 분류·필터링 방향을 바탕으로 구현한 프로젝트 정책이다. 문서의 정규식을 그대로 붙여 넣어 모든 언어·표현에 대한 완전탐지로 주장하지 않는다. 긴 숫자는 사업번호를 오탐할 수도 있다. 자유 문장 속 인명·질병·가족관계·상세 주소, 이미지·문서 첨부파일, 한글로 풀어 쓴 번호, 암호화·복잡한 난독화는 이 모듈만으로 완전히 판단할 수 없다.

## 4. 재현 가능한 구현 사례

다음은 실제 개인정보가 아닌 시험용 값이다.

| 입력 위치 및 시험 문자열 | 적용 결과 |
|---|---|
| 글 제목 `상담 요청 010-1234-5678` | `상담 요청 010-****-****` |
| 본문 `메일 qa@example.test` | `메일 ***@***.***` |
| 댓글 `이름: 김예시` | `이름: 김○○` |
| 답변 `계좌: 123-456-789012` | `계좌: [개인정보: 계좌번호 숨김]` |
| 본문 `０１０－１２３４－５６７８` 또는 제로폭 문자 삽입 | 정규화 후 010-****-****로 마스킹 |
| HTML 태그를 끼운 전화번호 + 이메일 | 정화 후 결합 텍스트를 검사하고 마스킹 텍스트로만 본문을 다시 만든다. |
| 비공개 / 관리자가 메인 노출을 꺼 둔 글 | 최근 질문·답변 메인 목록에서 제외 |
| 서버 예제에서 승인 후 본문·댓글 변경 | 승인 fingerprint 불일치로 공개 DTO를 반환하지 않음 |

```js
// 브라우저: privacy.js를 먼저 로드. 서버: 같은 UMD 파일을 require.

// result.text: '문의 ***@***.***'
// result.detected: true; result.findings에는 원문 값 없음.
```

`node --test tests/privacy.test.cjs`로 번호·이메일·유니코드·제로폭·엔티티·줄바꿈·이름/주소·최대길이·공개 DTO·승인 변경 검증을 수행한다. 실제 인명의 검출 한계도 명시적으로 테스트한다.

## 6. 공공기관 실서비스로 이관할 때의 필수 경계

정적 시안의 로컬 저장소·역할 전환은 사용자가 바꿀 수 있다. **클라이언트 JavaScript만으로 공공기관 보안 요구가 완성되지는 않는다.** 실제 서버는 로그인 세션/검증된 비회원 자격, 작성자 소유권, 관리자 권한, CSRF·요청 제한·감사기록을 검증해야 한다. 비밀번호는 서버에서 Argon2id 등으로 처리하고 원문·인증 토큰을 공개 DTO와 로그에 넣지 않는다.

동봉한 서버 예제는 신규 글을 `pending`·메인 비노출로 만들며, 검토 승인 후에만 공개 DTO를 만들도록 설계했다. 승인한 제목·본문·댓글의 SHA-256 fingerprint와 현재 데이터가 다르면 다시 비공개 처리한다. 이 fingerprint는 암호화·서명이 아니라 변경 여부 확인 값이며, 승인 상태를 쓰는 권한은 서버가 보호해야 한다. 탐지 0건이라도 문맥상 개인정보가 없는지 담당자가 확인해야 한다. 실제 HTTP 라우팅·DB 트랜잭션·인증 구현은 제공되지 않는다.

첨부파일을 허용하려면 서버의 문서 텍스트 추출·이미지 OCR·악성코드 검사·메타데이터 삭제·격리 저장과 별도 승인 경로가 필요하다. 이번 Q&A 에디터는 이미지·파일 첨부를 허용하지 않는다. 오류·분석 로그, 캐시·검색 색인·내보내기에도 공개 DTO 정책을 적용해야 한다. 기관은 배포 전 자체 보안성 검토와 개인정보 보호 담당자의 검토로 운영 정책을 확정해야 한다.

## 클릭형 구현 예시

기본 시안에는 설명 패널을 삽입하지 않습니다. 공개 Q&A 합성 게시물 P002에서 `김○○`를 누르면 기술 설명이, 나머지 제목을 누르면 글 상세가 열립니다. 본문의 `010-****-****`·`***@***.***`도 같은 방식입니다. 보라색 밑줄은 마스킹된 값에만 적용하며 원문은 링크 속성·숨겨진 DOM에 넣지 않습니다. 실제 처리 모듈은 `static/js/rms-enhance/ui/privacy-display.js`, 레이어 템플릿은 `templates/shared/privacy-tooltip.html`입니다. 닫기·바깥 클릭·Esc로 설명만 닫으며 기존 글 상세를 유지합니다.

### 탐지 방식과 재현 경로

- RMSPrivacy **1.2.0**은 안내서 주요 8종의 번호와 이메일·이름·주소를 처리한다. 생년월일·교육·건강·가족·고용·소득·계정·접속 IP·위치정보는 `진단명:`·`가족관계:`·`접속 IP:` 등 **명시된 필드의 값 전체**를 숨긴다. 자유 문장의 의미를 모두 판별하는 NER 기능이 아니다.
- 합성 입력·문서 근거: `reference/privacy/examples/board-scenarios.json`. 공개 배포 폴더에 이 원문 JSON을 복사하지 않는다.
- 압축소스에는 합성 입력과 마스킹 결과 `reference/privacy/examples/board-scenarios.masked.json`을 함께 넣는다. `node reference/privacy/examples/replay-board-scenarios.cjs`로 현재 폴더와 관계없이 실제 필터·공개 DTO 결과를 재현할 수 있다.
- 프로젝트 시안 생성기: `tools/build_privacy_examples.cjs`. 실제 `privacy.js`·`board-security.js`를 사용해 마스킹 후 `demo/data/privacy-scenarios.json`·`demo/generated/privacy-scenarios.js`를 만든다. 브라우저에는 마스킹한 데이터만 제공한다.
- 시안 초기 데이터: `demo/data/seed.json`. 재생성은 `node tools/build_privacy_examples.cjs` 후 `python tools/make_seed.py`. 전체 빌드도 사례 생성을 먼저 실행한다.
- 기존 저장자료는 새 버전에서 한 번 업그레이드한다. 초기 내용과 일치하는 합성 글만 교체하며 사용자가 수정한 글·댓글·노출 설정과 삭제한 기존 글을 보존한다. 업그레이드 뒤 삭제한 예시를 다시 만들지 않는다.
- HTML의 레이아웃 텍스트에서는 필드 값을, 태그를 제거해 결합한 텍스트에서는 분리된 번호·이메일 패턴을 재검사한다. 이미 마스킹한 필드를 잘못 합쳐 본문을 삭제하거나 원문이 복구되지 않도록 검증한다.
- PDF 복사 사례(P017)는 **게시판에 붙여 넣은 텍스트**만 검사한다. 원본 PDF·이미지의 OCR·숨은 레이어·메타데이터 검사나 파일 마스킹 기능을 구현한 것으로 표시하지 않는다.

검증은 제목·본문·댓글·관리자 답변에 걸친 합성 입력의 실제 마스킹 결과, 공개 DTO의 원문 부재, 3개 시안의 항목별 툴팁 및 PDF 링크, 기존 데이터 보존, 실제 DOMPurify 경로를 포함한다. 문맥상 개인정보·첨부파일·복잡한 난독화에는 앞 절의 담당자 검토·서버 접근통제 경계가 계속 적용된다.
