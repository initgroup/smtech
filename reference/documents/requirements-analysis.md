# RMS 기능 고도화 요구사항 분석

분석일: 2026-09-08. 근거: 제공된 제안요청서 HWP 본문을 직접 추출한 `rfp.txt`. 요구사항 상세 원문과 추출 줄 번호는 `requirements-catalog.json`, 전체 색인은 `requirements-index.md`에 기록했다. 아래 우선순위와 화면 구분은 선행개발을 위한 분석 제안이며 발주기관이 지정한 우선순위가 아니다.

## 1. 이 사업이 달성하려는 업무 목표

기업이 지역과 서류 제출 부담 때문에 지원사업을 이용하기 어려운 문제를 줄이고, 관리기관이 전문가 정보와 신청 증빙을 일관되게 관리하도록 만드는 사업이다. 새로운 시스템 전체를 만드는 사업보다 현행 RMS의 세 업무 영역을 고도화하는 사업으로 해석한다.

| 업무 영역 | 달성할 업무 결과 | 주요 사용자 | 기능 요구사항 |
|---|---|---|---|
| 기술닥터 | 최신 전문가 정보를 표준 기준으로 관리하고, 타지역 전문가까지 찾아 비교·매칭한 뒤 지원 실적을 확인 | 기업, 지역 관리기관(TP), 운영 관리자 | SFR-01~05 |
| 메인·소통 | 로그인과 자주 쓰는 업무에 빨리 접근하고, 업무별 질문과 기존 답변을 메인에서 찾아 해결 | 비회원 방문자, 로그인 사용자, 게시판·콘텐츠 관리자 | SFR-06~10 |
| 서류 간소화 | 기업 동의를 받아 증빙을 조회하고 신청 정보와 비교하며, 제출·실패·보완 상태를 기업과 관리기관이 함께 확인 | 신청기업, 사업관리기관, 연계 운영 담당자 | SFR-11~15 |

문서에 기재된 본사업 일정은 계약일부터 2026-12-10까지이며 예산은 부가세 포함 104,923,000원이다(추출 본문 26행 이하). 이 정보는 제공 문서의 사업 조건을 정리한 것으로 일정의 최신 상태를 별도로 확인한 것은 아니다.

## 2. 범위와 현행 업무의 연결

제안요청서의 현행 서비스 목록은 과제관리, 공고, 협약, 평가관리, 모니터링, 문의사항, 통계현황, 기술닥터, 공급기관, 지원이력, 소통관리다(추출 본문 140행 이후). 이 전체 업무를 모두 새로 구현하라는 요구는 아니다. 기술닥터·메인/소통·사업신청 증빙 흐름이 직접 개선 대상이며 다른 업무는 기존 진입점과 연계 관계를 보존해야 한다.

운영매뉴얼은 사용자 화면별 업무절차 매뉴얼이 아니라 서버·개발·형상·배포 운영 문서다. 내부 화면의 현재 필드·상태·API는 해당 문서만으로 확정할 수 없다. 공개 사이트에서 브라우저가 실제로 받은 HTML, CSS, JS, 리소스 경로, DOM 구조를 우선 근거로 사용하고, 로그인 후 내부 화면은 화면 설계 제안으로 표시한다.

## 4. 핵심 업무 흐름과 데이터 설계 제안

기술닥터는 `SMTECH 가상 사용자 선택 → 등록기관·전문분류·지역 입력 → 중복 확인 → 저장 → 통합 검색/비교 → 매칭 요청 → 처리상태/지원 실적 → 통계` 순서로 시연한다. 타지역 기관의 조회와 등록기관의 수정 권한이 다름을 같은 데이터로 확인해야 한다.

FAQ는 `메인 업무유형 선택 → 검색 → 주요/관련 답변 확인 → 전체 목록 또는 질문 상세 → 운영자가 유형·노출 변경` 순서로 시연한다. 민감한 글이 메인에 노출되지 않는 것이 단순 화면 디자인만큼 중요하다.

서류는 `사업 선택 → 필요서류 확인 → 정보제공 동의 → 가상 조회 → 성공/불일치/실패/미제공 분기 → 신청정보 비교 → 제출현황 확인 → 기관 보완요청 → 기업 파일보완 또는 재조회 → 처리이력` 순서로 시연한다. 명칭은 “자동반영”이지만 상세 요구는 불일치 자동 변경을 금지하므로 기존 값을 보존하는 비교·확인 화면이 우선이다.

| 제안 데이터 묶음 | 주요 내용 | 설계 이유 |
|---|---|---|
| 기술닥터 | 전문가 ID, 외부 사용자 참조, 등록기관, 기본정보, 갱신일, 상태 | 등록기관 권한·동일인 중복·미갱신 목록의 기준 |
| 전문분류 | 분류 코드, 부모 코드, 유형, 사용 여부, 지역 코드 | 계층·다중선택·검색·통계에서 같은 기준 사용 |
| 전문가 분류 연결 | 전문가 ID와 산업/기술/상담/지역 코드 연결 | 하나의 전문가가 여러 분야/지역에 속함 |
| 매칭·지원 실적 | 전문가·기업·요청기관·사업·기간·상태·지원결과 | 요청 건수와 실제 지원실적을 구분 |
| FAQ·소통 게시물 | 업무유형, 제목, 질문, 답변, 키워드, 공개 여부, 노출 여부, 답변상태 | 검색과 메인 공개정책을 일관되게 적용 |
| 메인 구성 | 콘텐츠 ID, 제목, 노출 여부, 순서 | SFR-10의 지속적 배치 변경을 데이터로 표현 |
| 사업·신청 | 사업 ID, 신청기업 ID, 신청정보, 필요서류 목록 | 사업마다 제출 조건이 다름 |
| 동의·조회 | 신청 ID, 동의 범위/시각, 서류종류, 조회일시, 응답상태, 오류사유 | 동의 선행과 조회 출처를 추적 |
| 제출·보완 | 신청·서류 ID, 제출방식, 상태, 파일 메타정보, 보완요청, 처리이력 | 기업·관리기관 화면이 같은 상태를 사용 |

이는 프로토타입용 논리 모델이며 현재 DB 테이블 또는 확정 ERD가 아니다. 조회/저장 모듈을 화면 이벤트에서 분리하고 JSON 입출력 구조를 문서화하면 추후 JSP·Controller·Service·DAO에 연결하기 쉽다. 브라우저 역할 전환은 화면 시연에 한하며 실제 접근통제는 서버에서 구현해야 한다.

프로토타입에서도 키보드 접근, 포커스 표시, 폼 레이블, 표 제목/헤더, 오류 안내, 대비, 반응형 배치, 공개 필터를 구현한다. 정식 웹접근성 인증이나 운영 환경 성능·보안·가용성 검증 완료를 의미하지는 않는다. 제안요청서의 법령·표준 명칭과 버전은 문서에 적힌 요구를 정리한 것이며 최신 법령 해석 자료로 사용하지 않는다.

## 8. 분석 한계와 원본 보존

HWP v5의 압축 본문에서 텍스트와 표 셀의 문단을 추출했다. 표의 내용은 문단 순서대로 보존했지만 셀 병합·페이지 배치·이미지 안의 글자는 복원하지 않았다. 운영매뉴얼의 이미지 43개와 제안요청서의 이미지 6개는 본문 텍스트 분석에 포함되지 않는다. 원본 HWP는 수정하지 않았으며 서버 주소·명시적 계정/연락처 등은 추출물에서 마스킹했다. 원문 페이지와 추출 텍스트 줄은 서로 다른 좌표다.
