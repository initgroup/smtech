# RMS 운영매뉴얼 개발환경·구조 분석

분석일: 2026-09-08. 근거: `RMS_운영매뉴얼_전달용_20260907.hwp`에서 추출한 `operations-manual.txt`. 이 문서는 현행 소스 실측 결과가 아니라 매뉴얼의 내용을 구분해 정리한 기록이다. 실제 공개 HTML·CSS·JS에서 확인한 정보가 충돌하면 실제 응답 소스를 우선한다.

## 문서의 성격과 신뢰 범위

파일명에는 20260907이 있지만 표지·개정이력은 작성일 2025-06-09, 버전 1.0, 최초 제정이다(추출 1~22행). 문서의 목적은 개발자·시스템관리자를 위한 서버 구성, 운영·개발 서버, 접근 경로, 개발환경, 코딩 표준, SVN, 배포 안내다. 사용자별 업무메뉴와 화면 조작을 상세하게 정의한 업무 운영매뉴얼은 아니다.

본문에 개발서버는 소스가 배포되지 않았고 개발 DB가 없다고 기재되어 있다(295~297행). 이는 작성 당시 문서의 상태이며 2026년 현재 상태로 단정할 수 없다.

주요 근거: 소프트웨어 구성 80~111행, 운영 Java 201행 부근, 개발 소프트웨어 325~357행, UTF-8 425~429행, 배포 797~807행. 서버 주소·실제 계정은 이 보고서에 싣지 않는다.

## 문서에서 확인되는 애플리케이션 구조

```text
tipa_rbms                         매뉴얼의 프로젝트 이름
├─ WebContent                     매뉴얼의 웹 컨테이너 표기
├─ src/main/resources-local
│  └─ props/globals.properties     로컬 DataSource 설정 위치 표기
└─ target/rbms-1.0.0               Maven 빌드 결과 폴더 표기

서비스 컨텍스트: /region/rms
Java 패키지 계열: gov.tipa.rbms
역할: Controller / Service / Dao / 필요 시 VO
화면: JSP
구성: Spring XML, MyBatis SQL-ID 명명 규칙
```

이는 매뉴얼에 각각 언급된 경로와 역할을 묶은 것이며 내부 저장소를 직접 조회하여 검증한 디렉터리 트리가 아니다. `WebContent` 표기와 Maven 경로가 함께 존재하므로 실제 JSP·정적 리소스 위치를 `src/main/webapp` 등으로 임의 추정하지 않는다. 외부 브라우저의 `/region/rms/...` 요청 경로는 서버 내부 파일시스템 경로와 다르며 JSP 원문·Controller·SQL을 보여주지 않는다.

### JSP 화면 구분 규칙

| 용도 | 매뉴얼 예시 |
|---|---|
| 검색조건 | `user/search.jsp` |
| 결과목록 | `user/list.jsp` |
| 입력 | `user/insertForm.jsp` |
| 수정 | `user/updateForm.jsp` |
| 통합 화면 | `user/index.jsp` |
| 트리 | `user/tree.jsp` |

매뉴얼은 소문자 파일명을 권고하면서 예시에는 `insertForm.jsp`와 `updateForm.jsp`를 사용한다. 따라서 실제 기존 파일명을 우선하고 새 파일은 팀의 현행 규칙에 맞춰야 한다. Java 메서드는 등록 insert, 수정 update, 삭제 delete, 단건 조회 get, 목록 조회 list와 명확한 동사형 이름을 사용한다. 프런트 JS도 불필요한 축약과 전역 함수 충돌을 피하는 것이 적합하다.

## HTML·CSS·JS 선행개발에 적용할 원칙

1. 실제 사이트의 문서 구조, 공통 헤더/메뉴, 정적 리소스 경로, 기존 CSS 클래스, JS 라이브러리와 이벤트 연결을 확인하고 근거 파일을 보관한다.
2. 기존 CSS 파일은 수정하지 않고 별도 스타일 파일을 뒤에 추가한다. 개선 화면의 최상위 요소에 전용 범위를 두고 신규 클래스에는 고유 접두어를 사용한다. 범위 밖 `body`, `button`, `table`, `input` 등에 영향을 주는 전역 재정의를 피한다.
3. 기존 플러그인·로그인·공고·메뉴 스크립트를 전체 복제해 재실행하면 실제 서버 요청이나 DOM 충돌이 생길 수 있다. 공개 소스의 구조와 필요한 스타일을 참고하되 데모 동작은 독립 모듈에 둔다.
4. HTML은 JSP로 옮길 수 있는 콘텐츠 단위로 구성하고 공통 헤더와 개선 본문을 분리한다. 시연 전용 도구모음·가상 역할 전환은 실제 인계 시 제거할 범위를 명시한다.
5. 화면 렌더링, 이벤트, 데이터 접근을 분리하고 가상 JSON의 필드·상태·오류 구조를 문서화한다. 나중에 데이터 접근 구현을 실제 Controller/API로 교체한다.
6. JSON 저장은 프로토타입 데이터만 다룬다. 브라우저 로컬 저장, JSON 내보내기/가져오기, 파일 서버 저장 중 실제 구현한 방식을 정확히 설명한다. 실제 인증정보나 기업 개인정보를 보관하지 않는다.
7. Python은 로컬 정적 미리보기 또는 가상 파일 입출력을 위한 도구로만 사용 가능하다. 최종 인계 자산은 HTML/CSS/JS/JSON으로 구성하고 Python 서버가 운영 시스템의 필수 백엔드인 것처럼 설계하지 않는다.

## 명확히 분리해야 하는 불일치·미확정 사항

| 항목 | 매뉴얼의 문제 또는 제한 | 판단 기준 |
|---|---|---|
| 문서 일자 | 파일 전달일과 본문 개정일이 다름 | 전달일로 모든 기술정보가 갱신되었다고 가정하지 않음 |
| JDK·Tomcat·DB | 운영환경과 개발환경 버전이 다름 | 운영·빌드 담당자와 실제 설정에서 확인 |
| 전자정부프레임워크 | IDE 명칭과 버전만으로 앱 런타임 버전을 확정하기 어려움 | 실제 pom.xml·라이브러리 목록이 필요 |
| HTML 표준 | 설명은 XHTML 1.0 Transitional, 예시 DOCTYPE은 XHTML 1.1 | 현재 사이트 실제 DOCTYPE 우선 |
| 소스 구조 | WebContent와 Maven 산출 경로가 함께 존재 | 공개 리소스 요청 경로와 내부 소스 경로를 별도로 기록 |
| 화면·메뉴 | 업무별 현재 폼·권한·코드·상태 자료 부족 | 공개 확인 화면과 요구사항 기반 제안 화면을 구분 |
| 데이터 연결 | DB 및 SMTECH 연결 안내가 있어도 현행 스키마·API 계약은 없음 | 프로토타입 필드명과 API 경로는 제안안으로 표시 |
| 수동 배포 일정 | 특정 요일과 승인·배포 과정이 기재됨 | 실제 배포 정책이 유지되는지 내부 인계 시 확인 |

원본 HWP는 보존했다. 텍스트 추출 과정은 `tools/extract_hwp.py`로 재현하며 이미지·도표 내부 글자는 이번 본문 추출 대상이 아니다.
