JDK 설치
기본적으로 자바 기반 애플리케이션 개발을 위해 JDK가 설치되어야 한다.
파일서버에서 JDK 파일 (jdk-8u144-windows-x64.exe) 을 로컬에 다운로드 받아 실행하여 설치한다.
자바 설치 완료 후 윈도우 콘솔에서 사용하기 위해 환경 변수에 등록한다.
※ 자바 설치 위치 및 환경 변수는 개발 소프트웨어 구성 정보를 참조한다.
Tomcat설치
웹 어플리케이션을 개발하고 즉시 테스트하기 위해 개발자 PC에는 웹 어플리케이션 서버인 Tomcat을 설치한다. JDK 버전에 따라 사용해야 하는 Tomcat버전이 달라지는데 JDK 1.8.0_144 기반이라면 Tomcat 9.0.X를 사용하도록 한다.
파일서버에서 Tomcat 파일(apache-tomcat-9.0.105-windows-x64.zip)을 다운로드 받아 압축 해제 하여 설치한다.

인코딩 변경
SMTECH 연구인력지원 및 지역사업 기능개선 구축 프로젝트는 향후 다국어 처리 등을 위해 UTF-8을 기본 인코딩으로 설정해 사용한다. 따라서 Eclipse 내 기본 인코딩 설정을 아래와 같은 방법으로 변경한다.
Window > Preferences > General > Content Types 을 선택하면 아래와 같은 창이 나타나는데 Text항목을 선택해 아래의 Default Encoding입력란에 UTF-8이라고 입력하고 Update 버튼을 클릭한다. Text항목 하위의 JSP항목도 마찬가지의 방법으로 입력 후 Update 버튼을 클릭한다.
그리고 JSP 자동 생성 시 사용되는 템플릿 내 인코딩 값도 UTF-8로 변경한다.
Window > Preferences > Web > Jsp Files 를 선택하면 아래와 같은 창이 나타나는데 역시 Encoding 값을 UTF-8로 변경해준다.
Validation 설정 조정
Eclipse는 프로젝트가 변경되거나 하는 경우 build와 함께 validation작업을 진행한다. 워낙 많은 Validation 체크를 하다 보니 성능이 좋지 않은 컴퓨터의 경우 시간이 오래 걸리는 경우가 많다. 특히 XML 관련 Validation 체크는 필수적으로 필요한 프로젝트가 아니면 꺼두는 게 조금 더 빠르게 build작업을 수행할 수 있다.
Window > Preferences > Validation을 선택하면 아래와 같은 화면이 나타난다. 여기에서 DTD Validator, XML Schema Validator, XML Validator의 Build시 체크를 해제하도록 한다.
Subversion 설정
SMTECH 연구인력지원 및 지역사업 기능개선 구축 프로젝트에서는 개발소스의 효율적인 관리와 배포 등을 위해 형상관리 도구로 Subversion을 사용한다. 각 개발자들은 정해진 소스 레파지토리로부터 프로젝트 소스를 내려 받고 개발 작업 완료 후에는 해당 레파지토리에 수정된 소스를 반영해야 한다.

컴파일러 레벨 확인
대부분의 경우 프로젝트를 소스 레파지토리에서 CheckOut 하면 설정도 함께 전달되어 오기 때문에 해당 자바 컴파일러 레벨 등도 정해져 있지만 간혹 이 컴파일러 레벨이 맞지 않아서 프로젝트 자체가 오류가 발생하는 경우가 있다.
이럴 경우 Package Explorer에서 해당 프로젝트를 선택 후 마우스 오른쪽 버튼을 클릭해 Properties를 선택 프로젝트 속성 정보 창을 띄운다.
속성 창의 왼편 노드 중 Java Compliler를 선택하고Compiler compliance level를 1.8로 맞추도록 한다.
Build Path 설정 확인
프로젝트 내에서 개발자 로컬 환경을 동일하게 하는 경우 레파지토리에서 프로젝트를 받아오면 같은 환경으로 구성되겠지만 JDK같은 경우에는 하위 세부 버전 등이 맞지 않아 프로젝트에 오류가 나타나는 경우가 발생한다.
- 이럴 경우 Package Explorer에서 해당 프로젝트를 선택 후 마우스 오른쪽 버튼을 클릭해 Properties를 선택 프로젝트 속성 정보 창을 띄운다.
- 속성창의 왼편 노드 중 Java Build Path를 선택하고 Libraries 탭을 선택하고Tomcat과 JRE등이 올바르게 설정되었는지 확인한다.
- Unbound가 나타나거나 프로젝트에서 지정한 Tomcat이나 JRE 버전이 맞지 않는 경우 해당 라이브러리를 선택 후 Edit버튼을 클릭해 올바른 정보로 재설정 해준다.

서버코딩 표준
개요
코딩 표준의 필요성
프로그램의 코딩 표준은 다음과 같은 이유로 프로그래머에게 있어서 중요성을 지닌다.
소프트웨어의 생명주기에 있어서 비용의 80%이상이 관리에 소요된다.
코드표준은 소프트웨어의 가독성(Readability)을 높여 주며 개발자로 하여금 새로운 코드를 보다 빠르고 완벽하게 이해하도록 한다.
제품으로써 소스코드를 납품해야 할 경우 다른 제품과 마찬가지로 코드를 잘 정리하고 깔끔하게 해야 한다.
재 작업으로 발생하는 error를 예방 할 수 있다.
이를 위해 표준이 잘 적용되도록 하기 위해서는 소프트웨어 작성자 모두가 코딩 표준을 반드시 준수해야 한다.
코딩 표준이 적용될 수 없는 경우
표준적용에 예외가 발생하는 경우에는 표준을 저해하는 잠재적인 가능성 및 표준이 적용되기 이전에 발생한 어떤 조건이나 상황 및 대처방식을 문서화 해 놓으면 다른 사람으로 하여금 표준을 지키지 않은 코드를 이해하는데도 편리를 제공하고 표준자체를 보다 견실히 하는데도 도움이 된다.
명명규칙 (Naming Convention)
명명 규칙은 프로그램을 읽기 쉽고 보다 이해하기가 좋게 하며 또한 코드를 이해하기 쉽도록 하는 구분자를 사용함으로써 보다 많은 정보를 제공한다.
공통적으로 준수해야 할 사항은 아래와 같다.
- 이름으로 20자 이상을 사용하는 것은 좋지 못하다.
- Full name을 권장하며, 축약형은 지양한다. (Msg, Appnd...)
- 널리 알려진 축약형을 사용할 때 첫 문자만 대문자를 사용한다. 
예) loadXmlDocument()
- 비슷한 이름은 사용을 배제한다.
예) persistentObject와 persistentObjects

패키지
각 시스템 또는 기능 별로 패키지를 분류해 작성한 클래스들은 관리 효율성이 증대된다. 패키지의 네이밍은 아래와 같은 3단계의 구조에 맞추어 작성한다. 각 패키지는 가능한 바로 인지 가능한 의미 있는 단어를 사용하되 단어가 너무 길어질 경우 적절한 축약형 단어를 사용할 수 있다. 기본 룰은 아래와 같다.
- 선언 위치 : package는 Java의 Source file(*.java)에서 그 어떠한 선언보다 맨 처음 선언이 되어야 한다.
- 선언 개수 : package는 Java의 Source file(.java)에서 선언이 된다면 반드시 단 한번 선언이 되어야 한다. 또한 모든 Java Source 에는 package 사용을 원칙으로 한다.
- 패키지 이름은 모두 소문자로 구성된다.

클래스
클래스 이름은 기본적으로 SUN의 표준 명명 규칙을 준수한다.
- 클래스 이름의 시작은 대문자로 시작한다.
- 클래스 이름이 두 단어 이상으로 구성되는 경우 이어지는 단어의 첫 글자는 대문자로 시작한다. (camel-case)
- 클래스 이름은 명사형이어야 한다.
- 클래스 이름에는 가능한 약어를 사용하지 않으며, 대문자가 겹치는 경우도 없도록 한다.
- 클래스 이름은 될 수 있는 한, 구체적으로 표현하되 너무 긴 이름은 사용하지 않도록 한다.
- 추상 클래스의 경우에는 Abstract 를 prefix로 사용한다.
- 구현 클래스의 경우에는 Impl 을 suffix로 사용한다.

- 메소드명은 소문자로 시작하고 두 단어 이상으로 구성되는 경우 다음 단어의첫 글자는 대문자로 표기한다.
예) getUser(), insertUserInfo()……
- 메소드명은 동사형으로 표기한다.
- 멤버변수에 접근하는 getter와 setter메소드들은 멤버변수 명 앞에 각각 get 과 set을 붙여 사용한다.
예) String firstName =>  getFirstName(), setFirstName(String name)
- 단 Boolean 멤버변수에 접근하는getter메소드는 멤버변수 명 앞에 is를 붙여 사용한다.
예) boolean available =>  isAvailable()

변수
변수 이름은 기본적으로 SUN의 표준 명명 규칙을 준수한다.
- 변수는 모두 의미있는 단어의 조합으로 사용한다.
- 특별히 정해진 약어 이외에는 Full-Word 를 사용한다.
- 변수 이름은 소문자로 시작하고 두 단어 이상으로 구성되는 경우 두 번째 시작하는 단어의 첫 글자는 대문자로 표기한다.
예) firstName, username……
상수
상수 이름은 기본적으로 SUN의 표준 명명 규칙을 준수한다.
- 상수의 성격을 갖는 변수의 경우에는 모두 대문자로 표기한다.
- 상수 변수 명이 두 단어 이상으로 구성되는 경우 ‘_’ 로 연결한다.
예) MIN_VALUE, MAX_VALUE ……
- 상수인 경우 더 이상 값 설정이 없으므로 final 키워드를 사용해 선언한다.
예) private final String MIN_VALUE = 0;

형상 관리 정책
개요
프로젝트 내에서 개발되는 모든 소스코드관련 산출물들은 형상관리가 되어야 한다. 기본적으로 SVN(Subversion)을 사용하여 형상관리 한다.
관리대상
자바 프로젝트 : 자바 소스코드 및 테스트 코드, 웹 관련 모든 소스코드를 포함한 프로젝트 설정

형상 관리 툴 사용 방안
자바 프로젝트 관리
SVN 클라이언트는 크게 이클립스 내 사용하는 방법으로 한다.
SVN 저장소 연결
1) SVN Repositories 뷰를 연다.(또는 SVN perspective)
2) New 버튼을 클릭해서 새로운 Repository 연결 페이지를 띄운다.
3) 연결하고자 하는Repository 정보를 입력한다.
4) SVN이 정상적으로 연결되었는지 확인한다.
새 프로젝트 공유
1) 새롭게 프로젝트를 공유하고 싶은 경우 이클립스의 [Team>Share Project] 메뉴를 사용한다.
2) 다음 나오는 창에서 SVN을 선택한 후, 올리고자 하는 대상 Repository를 선택한다.
3) 공유되는 위치 정보를 확인한 후, Finish를 선택한다.
4) 커밋하는 프로젝트 내용을 확인하고, 코멘트를 입력한 후 OK를 선택해 프로젝트 공유를 완료한다.
Repository 프로젝트 내려 받기
Repository에 있는 프로젝트를 로컬에 받고 싶은 경우, 'checkout' 커맨드를 통해서 프로젝트 전체를 한 번에 내려 받을 수 있다.
소스 커밋 / 업데이트
변경된 소스를 SVN repository에 반영하는 것을 커밋(commit)이라 한다. 업데이트(update)는 SVN repository에 있는 소스 정보를 로컬 프로젝트에 반영하는 것을 의미한다.
1) 이클립스에서 커밋과 업데이트는 Team 팝업 메뉴의 commit/update 커맨드를 통해 수행된다.
2) 커밋의 경우 커밋 할 소스를 확인하는 다이얼로그 창이 한 번 더 뜨며, 업데이트의 경우 바로 업데이트를 수행하게 된다.
3) 커밋 시에는 반드시 커밋 되는 소스나 이슈에 대한 설명을 반드시 명시해 주어야 한다.
커밋과 업데이트를 별도의 커맨드로 수행할 수 있지만, 이 방법보다는 로컬 프로젝트와 repository의 프로젝트를 비교해서 직접 반영하는 방법을 사용하는 것이 좋다.
4) 이 때 자동으로Team Synchronizaing perspective로 이동하게 되며, 로컬과 repository의 프로젝트 내용을 비교하면서 직접 커밋, 또는 업데이트를 수행할 수 있다.
